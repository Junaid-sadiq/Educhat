Functor and monad in math

  • The terms originate from category theory
  • functor: mapping between categories
  • monad: endofunctor, where "endo" means mapping from one category to the category of the same type

functor and monad

  • functor has map
  • monad has also flatmap
    • enables keeping the object flat
      • e.g., no nested arrays or Promises

Monad as a design pattern

Generically
  1. type(constructor)
  2. bind(flatmap)
  3. return|pure|unit
Array
  1. new Array(1,2,3)
  2. map/flatmap
  3. Array.of(1,2,3)
Promise
  1. new Promise((resolve, reject)...)
  2. then()
  3. Promise.resolve()

Benefits

  • abstracts away side-effects
  • makes code more composable and reusable

Example

const safeStringLength = 
  (str) => Maybe.of(str).map((s) => 
    s.length).getOrElse(0); //return and bind
console.log(safeStringLength(null)); // 0 
console.log(safeStringLength('Hello')); // 5

// Define a monad object with of and chain methods
const myMonad = {
  of: (value) => {
    return {
	  value: value,
	  chain: (fn) => fn(value),
    };
  },
};
// Define a normal function
function addOne(num) {return num + 1;}

// Transform the function into a monad
const addOneMonad = (num) => {
	return myMonad.of(num).chain((val) => myMonad.of(addOne(val)));
};
// Use the monad to add one to a number
const result = addOneMonad(3); // { value: 4, chain: [Function] }

Applying mathematical concepts to computer science (CS)

  • math is more abstract than CS
  • FP languages closer to math than imperative ones
    • static types and pure functions guarantee more math-like behaviour, thus functors and monads in Haskell (FP) comply with category theory better than in JS. thus, e.g. category theory applies only to a certain extent in CS.

    With these disclamers, we draw the analogies between:

    • functor and an array with well-behaving map() function
    • monad and a Promise, where then() maps a Promise to a Promise and flattens the structure (no Promise inside a Promise).
    • monad = functor + flatten

Promise chaining

Promise is a monadic structure with two tracks: separate resolved and rejected tracks.

If Promise is resolved, the execution continues to the next then(), if defined.

If Promise is rejected, it has options of continuing to the next then(), if it provides a function for handling rejections. Without it, the rejection continues to catch() branch.

Happy (right) and Sad (left) paths

Lots of monads build on this duality: success or not. Examples range from Promises to Maybe and Either (in monet.js).

Monad have a potential to replace try-catch error handling: monad may bear both alternatives, success and failure, and methods acts accordingly: in case of error, the error is handled, whereas success is the default behaviour and is treated as such.

This blog shows how to do the trick with either function. The implementation uses separate classes Left and Right: 

function either(leftFunc, rightFunc, e) {
	return (e instanceof Left) ? 
		leftFunc(e._value) : rightFunc(e._value);
}

Dynamic polymorphism through duck typing

Method selection of both, Left and Right, should be identical. Thus, no matter which one is returned, methods are callable without checking the type.

This uniformity or methods is called Duck typing: "If it walks like a duck and it quacks like a duck, then it must be a duck".
Duck typing does not mandate the inheritance of a same base class (e.g., Animal) that is the way of implementing static polymorphism in object-oriented programming (OOP).

Railway-oriented programming (ROP)

ROP builds on these two tracks: failure (left) and success (right). A natural choice is to implement ROP based on, e.g., Promise or Either, see dorp.io's Promise-based implementation.
