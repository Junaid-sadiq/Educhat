It co-operates with the call stack that maintains call frames to keep track of the current context and executes the topmost command (LIFO). Event loop moves tasks from queues to the call stack: sync commands in the order of execution order; async callbacks are first put on a queue, implying a delayed execution. Macro- and micro-task queues Async Web API calls are put in the task queue, these tasks are also called macro-tasks. APIs include event emitting, timeouts and AJAX calls, see the exhaustive list by Mozilla developers In frontend side, these tasks coordinate browser components and have different priorities: Jobs (micro-tasks) do not interact with a browser but are dedicated to the use of the JS interpreter. Promise Promises to the rescue Promise represents an ansynchronous result that completes enventually. Before Promise is settled it is in pending state. When the result is got, pending Promise moves either to: fulfilled state, i.e., it is successfully resolved. The promise may move to the next then() function. rejected state, Promise jumps either to the reject section of next then() or to catch() In addition to then() and catch(), finally() is available as the completing last action for both branches. Promises in real life have a similar pattern For example: Mom is happy and promises to buy you a new phone, she goes shopping (pending). A new phone was bought, still midst of "eventual completion", because to get it in use, a protection glass (then) and a SIM card (then) has to be bought as well. After it, the promise is fulfilled. const isMomHappy = true; // Promise const willIGetNewPhone = new Promise( function (resolve, reject) { isMomHappy ? resolve({ brand: 'Jolla', color: 'yellow' }): reject(new Error('mom is not happy')); } ); willIGetNewPhone .then(data => { data["accessories"] = ["protection-glass"]; return Promise.resolve(data); }) .then(data => { data["sim-card"] = true; return Promise.resolve(data); }) .then(data => console.log(data)) .catch(err => console.log(err)); Promise API Methods: // the methods of moving from pending to settled Promise.resolve() //"happy" path, Promise is fulfilled Promise.reject() //"sad" path, Promise is rejected // the methods that determine what happens to a Promise after settling Promise.prototype.then() //the next phase after a resolved promise, returns a promise Promise.prototype.catch() //catches any error (reject) of the promise chain Promise.prototype.finally() //final actions at the end of the chain // multiple promises taken as a param Promise.all() //resolves promises concurrently, if any rejects, all() rejects Promise.allSettled() //like reject-permissive all(), resolves when all are settled Promise.any() //returns the first fulfilled promise of an arr Promise.race() //like reject-permissive any() Thenable At minimum, thenable implements then() method, for example: const thenable = { then: function (onFulfilled) { setTimeout(() => onFulfilled("it is fulfilled"), 10); } }; Promise.resolve(thenable) .then(data=>console.log(data)); // Or Promise.resolve() .then(data=>thenable) .then(t=>console.log(t)); Thenable serves as a simplified executor that may be reused in resolve situation. Continuation Continuation overlaps partially with closure, but is a wider and more abstract concept bonding with a control flow. In addition to callbacks, GOTO and exception handling (try-catch-finally) exploit continuations: before jumping from the current point of execution to another, the execution state is reified into a callable entity (similarly to enclosing lexical scope into closure in case of a callback) that enables switching between contexts. E.g., promise chain of then() passes the continuation. Continuation-passing style (CPS) In CPS, a function calls a callback instead of simply returning. The call must be the last action: the constraint is the same as in a tail recursion - and for the very reason: no need to return ⇒ the caller's activation record in the stack is removable, the removal eliminates memory overhead. Normal control flow is like Finnish baseball on the left: home is like the main program, a ball representing the current execution point, hitting the ball is like calling callback. After its exection, the control returns to the home base (main). On the contrary, CPS is like a relay race, continuation being a baton passed from a runner (callback) to runner, not returning home in between. CPS example function cps(x,done){ done(x*x); } - no return, but a callback.
