JavaScript features

  • dynamically and loosely typed scripting language
  • prototypal inheritance, classes built on top of that
  • functions are first-class citizens, thus acceptable as variables and parameters, making JS prone to functional paradigm

(A)Synchronous Communication

Synchronous

Alice has a question. Alice phones Bob. Bob answers the question. Alice has the answer.

But what if Bob isn't available?

Asynchronous

Alice has a question. Alice sends Bob an email. Some time later Bob sends the answer back via email. Alice has the answer.

Blocking commands

In JavaScript, a command is run till the end, the model referred to as run-to-completion. Since other things are on-hold during its execution => costly commands will result in a deteriorated user experience:

while(true);

To avoid blocking in a single-threaded system limits the means to:

splitting heavy commands async execution by using
  • to sub-programs
  • by arity (i.e., currying)
  • async versions of functions, both versions may be available, e.g., fs.readFileSync()/fs.readFile()
  • event emittance/message posting
  • async callbacks such as setTimeout() that move task to the task queue
  • promises (or async/await), move job to the job queue
  • e.g., child processes, web workers or generators (out of the scope of WebDev1)

Being single-threaded and event-driven

Pros

  • no threads, no tricky synchronization with semaphores, locks, mutexes
  • no race conditions either, thus no deadlocks, livelocks, or starvation
  • shared state, more deteministic behaviour
  • no overhead of copying shared resources or managing thread states on stack

Cons

  • free synchronization and context are gone
  • more flexibility, but more responsibility (inversion of control)
  • sync exceptions exist like alert() or sync XHR, a good practice is to avoid them
  • fragmented code, control flow becomes obscured
  • ..including error management
  • cannot fully exploit the power of multiple processors

Single thread: event loop

Fig. The event loop moves tasks from queues to callstack (in node.js, @deenjohn)

Event loop is the main actor in the JS concurrency model.

It co-operates with the call stack that maintains call frames to keep track of the current context and executes the topmost command (LIFO).

Event loop moves tasks from queues to the call stack:

sync commands in the order of execution order;

async callbacks are first put on a queue, implying a delayed execution.

Macro- and micro-task queues

Async Web API calls are put in the task queue, these tasks are also called macro-tasks. APIs include event emitting, timeouts and AJAX calls, see the exhaustive list by Mozilla developers

In frontend side, these tasks coordinate browser components and have different priorities:

Jobs (micro-tasks) do not interact with a browser but are dedicated to the use of the JS interpreter.

Callback

Callback, a function passed as a param

Array functions (forEach(), map(), filter(), reduce()) exploit callbacks synchronously; function is called on each item.

Yet being asynchrous exposes the full meaning of a callback as a function that is "called back" when its time has come: the desired event has been triggered (e.g., a user clicks something), a client gets server's response, or the JSON parser gets lengthy JSON message parsed, for instance.

In JS, callbacks are often event handlers, set to the listen for a trigger, which explains why JS is called event-driven: nothing happens without events.

Callbacks: either sync or async

const fillElemSync = (newElem, str) => 
[...str].forEach(ch => {
  newElem.innerHTML = newElem.innerHTML + `${ch}`;
  alert(ch);
});
const fillElemAsync = (newElem, str, i=0) => {
  if (i==str.length) return;
  newElem.innerHTML=newElem.innerHTML+str[i];
  setTimeout(()=>fillElemAsync(newElem, str, ++i),200);
};

elem.parentNode.appendChild(newElem);  //added as a sibling of h2

Promise

Promises to the rescue

Promise represents an ansynchronous result that completes enventually.

Before Promise is settled it is in pending state.

When the result is got, pending Promise moves either to:

  1. fulfilled state, i.e., it is successfully resolved. The promise may move to the next then() function.
  2. rejected state, Promise jumps either to the reject section of next then() or to catch()

In addition to then() and catch(), finally() is available as the completing last action for both branches.

Promises in real life have a similar pattern

For example: Mom is happy and promises to buy you a new phone, she goes shopping (pending).

A new phone was bought, still midst of "eventual completion", because to get it in use, a protection glass (then) and a SIM card (then) has to be bought as well. After it, the promise is fulfilled.

const isMomHappy = true;
// Promise
const willIGetNewPhone = new Promise(
  function (resolve, reject) {
    isMomHappy ? 
      resolve({ brand: 'Jolla', color: 'yellow' }):     
      reject(new Error('mom is not happy'));
  }
);
willIGetNewPhone
  .then(data => {
    data["accessories"] = ["protection-glass"];
    return Promise.resolve(data);
  })
  .then(data => {
    data["sim-card"] = true;
    return Promise.resolve(data);
  })
  .then(data => console.log(data))
  .catch(err => console.log(err));

Promise API

Methods: 

// the methods of moving from pending to settled  
Promise.resolve()            //"happy" path, Promise is fulfilled
Promise.reject()             //"sad" path, Promise is rejected

// the methods that determine what happens to a Promise after settling 
Promise.prototype.then()     //the next phase after a resolved promise, returns a promise
Promise.prototype.catch()    //catches any error (reject) of the promise chain
Promise.prototype.finally()  //final actions at the end of the chain

// multiple promises taken as a param
Promise.all()                //resolves promises concurrently, if any rejects, all() rejects
Promise.allSettled()         //like reject-permissive all(), resolves when all are settled
Promise.any()                //returns the first fulfilled promise of an arr
Promise.race()               //like reject-permissive any()

Async/await

async keyword

Used in in a function declaration or expression

// declaration:
async function foo(){}
// expression:
const bar = async () =>{}
console.log(foo() instanceof Promise, bar() instanceof Promise)

Other than async keyword, function may look normal, but it is anticipated to be a slow poke and to return a Promise either explicitly or implicitly: even if a plain value is returned, it will be wrapped inside a Promise.

Adding async causes a chain reaction: its caller must be made async, and so forth; the chain ends at the main level. Alternatively, the async part may be isolated to its own block.

https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/async_function

https://alligator.io/js/async-functions/

async IIFE

One means to have an async block is to use IIFE = Immediately Invoked Function Expression (IIFE).

The simplest IIFEs need neither name nor arguments, e.g.:

(async () => {
  const res = await Promise.resolve("Go, IIFE, GO!");
  console.log(res); // Go, IIFE, GO!
})()

Having parenthesis around a function declaration converts it as an expression.

The expression is self-invoked by the last trailing parenthesis, discussed here in more detail

AsyncFunction constructor

In addition to keyword async, async functions can be instantiated with AsyncFunction:

new AsyncFunction([arg1[, arg2[, ...argN]],] functionBody)

For example:

const AsyncFunction = Object.getPrototypeOf(async function(){}).constructor;
function createAsync(){
  return new AsyncFunction('a', `return new Promise((resolve) => {
      setTimeout(() => {resolve(a)}, 1000)
  });`);
}
createAsync()("WebDev1").then(data=>console.log(data));
(async function myFunction(){
  const res = await createAsync()(1);
  console.log(res);
})()

The constructor enables also async testing:

const isAsync = myFunction.constructor.name === "AsyncFunction";

await

await waits for the resolution of a Promise and pauses the execution until that.

async function may (or may not) contain an await statement, whereas..

await statement must reside inside async block, otherwise:

  await Promise.resolve("yes!")
    ^^^^^
  
  SyntaxError: await is only valid in async function

async/await

implemented as syntactic suger on top of Promises.

await causes async function to pause until a Promise is settled. Thus, async/await resembles sync mode but is less prone to blocking.

Refactored fetch with async/await

Below, the value of the first await expression is that of the resolved response, and the second, the parsed json. Parsing may take time.

const fetch = require('node-fetch');
const url ='https://jsonplaceholder.typicode.com/todos/1';
(async ()=>{                          //as IIFE            
  let response = await fetch(url);    //the 1st
  let parsed = await response.json(); //the 2nd
  console.log(parsed);
})()

Promise.all()

Promise.all()

Starts multiple Promises in parallel and waits for them all to finish.

After all the Promises are fulfilled, returns a single Promise, that contains resolved values as an array:

const proms = [1, 2, 3].map(val => Promise.resolve(val));
Promise.all(proms)
  .then(res=>console.log(res, typeof res, Array.isArray(res)));    
// Array [1, 2, 3] 'object' true

However, Promise.all() rejects if any of the Promises rejects.

More here.

Promise.all() resolves Promises concurrently

Time consumption of await calls inside async block is got as a sum.

Promise.all() makes the calls concurrently, thus, the time approaches the time spent by the longest call:

fetch() example with Promise.all()

Here, fetching and json parsing are done in parallel. First, an iterable of Promises (prom1 and prom2) is passed as an input parameter.

const fetch = require('node-fetch');
const url1 = 'https://jsonplaceholder.typicode.com/todos/1';
const url2 = 'http://lissu-api.herokuapp.com/';
const prom1 = fetch(url1);
const prom2 = fetch(url2);
Promise.all([prom1, prom2])
    .then(response => {
        Promise.all([response[0].json(), response[1].json()])
            .then(parsed => 
            parsed.forEach(json => console.log(JSON.stringify(json))));
    });

The iterable is returned as a resolved value: response array. The next Promise.all() takes another array of Promises, this time the return values of Body.json() calls. The innermost then() prints the resolved values.

Closure

implies lexically-scoped name binding: a closure stores a function together with its environment including parameters and variables. In Javascript, lexical scoping is defined by function's scope: each function creates a new scope.

Closure enables encapsulation and variable scoping (private, public), thus fostered, e.g., the implementation of objects.

An inner function sees the outer-function variables, not the contrary:

const d = 7;
((a=1,b=2)=>{
  const c = a + b + d;
  console.log("closure sum=",c)
})()
console.log(c); //ReferenceError: c is not defined

Specificity rule: variables are searched in the descending order of specificity, first the closest scope.

Scoping with closures

const makeCounter = function() {
  let privateCounter = 0;
  function changeBy(val) {
    privateCounter += val;
  }
  return {
    increment: ()=>changeBy(1),
    decrement: ()=>changeBy(-1),
    value: ()=> privateCounter
  };
};
const counter = makeCounter();
counter.increment();

Continuation

Continuation overlaps partially with closure, but is a wider and more abstract concept bonding with a control flow.

In addition to callbacks, GOTO and exception handling (try-catch-finally) exploit continuations:

before jumping from the current point of execution to another, the execution state is reified into a callable entity (similarly to enclosing lexical scope into closure in case of a callback) that enables switching between contexts.

E.g., promise chain of then() passes the continuation.

Continuation-passing style (CPS)

In CPS, a function calls a callback instead of simply returning.

The call must be the last action: the constraint is the same as in a tail recursion - and for the very reason:
no need to return ⇒ the caller's activation record in the stack is removable, the removal eliminates memory overhead.

Normal control flow is like Finnish baseball on the left: home is like the main program, a ball representing the current execution point, hitting the ball is like calling callback. After its exection, the control returns to the home base (main). On the contrary, CPS is like a relay race, continuation being a baton passed from a runner (callback) to runner, not returning home in between.

CPS example

function cps(x,done){
  done(x*x);
}

- no return, but a callback.
